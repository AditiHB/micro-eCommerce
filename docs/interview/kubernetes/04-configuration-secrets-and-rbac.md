# Configuration, Secrets & RBAC

### Q: How does this repo decide what goes into a plain environment value versus a Kubernetes `Secret`?

**A:** Strictly by sensitivity: anything that isn't a credential is inlined directly as a plain `env:` value in
the Deployment manifest itself (Eureka URL, Kafka broker list, JWK-set URI, issuer, audience, Redis
host/port) — visible to anyone who can `kubectl describe` the pod, which is fine, since none of it is secret.
Anything that **is** a credential (`EUREKA_PASSWORD`, `CONFIG_SERVER_PASSWORD`, `SPRING_DATA_REDIS_PASSWORD`,
each service's own DB password) is sourced via `secretKeyRef` against one shared `Secret` named
`ecommerce-secrets` instead. Worth knowing as a real detail, not just the general pattern: this repo's business
services don't actually use a `ConfigMap` object for their own non-sensitive config at all under `k8s/base` —
that centralization role is already filled at the application layer by Spring Cloud Config Server (see
[../microservices/02](../microservices/02-service-discovery-and-configuration.md)), so a second,
Kubernetes-native config-centralization mechanism alongside it would be redundant rather than complementary.

### Q: Where does `ecommerce-secrets` actually come from, and why would a content change to it *not*
automatically restart the pods that reference it?

**A:** It's generated by Kustomize's `secretGenerator` (`k8s/base/kustomization.yaml`), sourced from a
git-ignored `generated/secrets.env` file that a setup script (`scripts/gen-k8s-secrets.sh`) writes from the
operator's own `.env` — no credential is ever committed to the repository itself.

The subtle part: Kustomize's generators normally append a content hash to the generated object's name (so
`ecommerce-secrets` might actually become `ecommerce-secrets-7f2a9c1b`), specifically so that changing the
underlying secret content produces a *new* object name, which changes what every referencing Deployment points
at, which is exactly what triggers Kubernetes to roll those pods automatically. This repo's
`kustomization.yaml` sets `generatorOptions.disableNameSuffixHash: true` — the generated `Secret` keeps a fixed
name across regenerations. That means **updating the secret's content does not, by itself, cause a rolling
restart of anything referencing it** — existing pods keep running with whatever value was mounted/injected at
their own last start, and would only pick up a changed credential on their *next* restart for an unrelated
reason (a deploy, a manual restart, a crash). This is a real operational tradeoff worth being able to name: a
fixed name is simpler to reference and reason about, but it means secret rotation requires an explicit,
deliberate pod restart as a second step — it isn't automatic the way a hashed-name generator would make it.

### Q: What does the RBAC setup here actually grant, and does any of this project's code actually use it?

**A:** `k8s/base/02-rbac.yaml` gives each service its own `ServiceAccount` (`order-service-sa`,
`inventory-service-sa`, etc.) plus a least-privilege `Role`. Honest answer, stated directly in the manifest's
own comment: **none of these services actually call the Kubernetes API themselves** — there's no Kubernetes
client library in use anywhere in this codebase, and the `secretKeyRef`/env-injection mechanism that actually
delivers secrets to pods is resolved by the **kubelet**, not by the pod's own in-cluster RBAC permissions. So
this RBAC setup doesn't currently change what any running service can actually do. It exists, per the same
comment, as *"a genuine, working least-privilege RBAC example for learning purposes, and as the hook point if
any service ever does need API access later."* Worth being precise about this rather than overstating RBAC's
current role here: it's correctly-structured, real RBAC — just not yet load-bearing, because nothing in this
system needs to talk to the Kubernetes API yet.

### Q: This repo's own RBAC file mentions replacing a *broken* bundled manifest — what was actually wrong
with it, and why is that a good example of checking a manifest rather than assuming it works?

**A:** The replaced file shipped a `PodSecurityPolicy` object — an API kind that was **removed from Kubernetes
entirely in 1.25**, which this project's own documented minimum supported version already is, meaning that
manifest could never have applied successfully to any cluster this project claims to support; it would have
failed outright, not degraded gracefully. It also shipped an `audit.k8s.io/v1` `Policy` object, which — despite
having a `kind` and `apiVersion` that look exactly like an ordinary applyable Kubernetes resource — isn't one at
all; an audit policy is consumed by the API server via its own `--audit-policy-file` startup flag, never via
`kubectl apply`. Both were simply dropped rather than carried forward in a broken state. The lesson worth
stating plainly: a YAML file that is syntactically valid and *looks* like a normal Kubernetes manifest can still
reference a resource kind that doesn't exist on your actual cluster version, or isn't managed via `kubectl`
at all — "it parses" and "it's a real, apply-able resource on this cluster" are two separable claims, and
checking the second one is exactly what caught this.
