# Security hardening: what changed, what was verified, what is still open

This document records the security work done in response to the senior-engineering review of this repository
(roadmap items **P0-1 secrets and defaults**, **P0-2 authorization holes**, **P2-12 identity**), plus the
**HashiCorp Vault** and **smallstep** certificate-management additions. It is deliberately explicit about what was
*run and observed* versus what was only *written*.

## 1. Summary

| Area | Result |
| --- | --- |
| **Secrets and defaults (P0-1)** | No credential is stored in the repository any more. Every secret is generated on your machine (`scripts/gen-env.sh`), compose refuses to start without it, services refuse to start without their identity settings, seeded privileged accounts are gone, and the TLS private key and session-ticket key are out of the tree. History still needs a purge ([section 6](#6-purge-the-committed-key-from-git-history)). |
| **Authorization (P0-2)** | Deny-by-default role matrix asserted by 187 generated test cases, plus object-level ownership (a customer sees only their own customer record and orders), plus validated stock quantities. |
| **Identity (P2-12)** | Keycloak issues RS256 tokens; the gateway and every service verify signature, expiry, issuer and audience against Keycloak's keys. No shared signing secret, no login endpoint, no per-service `users` tables. Service-to-service calls use OAuth2 client credentials. |
| **Vault** | Opt-in overlay: AppRole login per service, per-service least-privilege policies, KV secrets, and short-lived DML-only Postgres logins minted per instance. Secrets are removed from the containers' environment. |
| **smallstep** | Opt-in overlay: internal CA (step-ca), 24-hour certificates for nginx, Keycloak and Vault, automatic renewal, services trusting the platform CA through Spring SSL bundles. |

## 2. Before and after

| Question | Before | After |
| --- | --- | --- |
| Who signs tokens? | every service, with one HMAC secret that had a **public default** | Keycloak only (RS256); services hold public keys |
| Can a default deployment be forged into admin? | yes (`karate_admin` seeded; secret in compose, k8s manifest and `application.yml`) | no secret to guess; no seeded account; no default for issuer/audience/secrets |
| Any logged-in user can refund a payment / set stock / complete someone's order for $0.01 | yes | 403 |
| Any logged-in user can list every customer's name and email, and every order | yes | 403 / only their own |
| A negative stock "reservation" | **adds** stock (reproduced: 5 → 55) | 400, stock untouched |
| Database accounts | one shared `ecommerce_user` / `ecommerce_password`, committed | one owner role per service, generated passwords; with Vault, per-instance DML-only logins |
| Cross-service database access | possible (one shared account) | refused (`CONNECT` revoked from `PUBLIC`; verified) |
| Redis, Grafana, Eureka, config server | open / `admin123` / `permitAll` | passwords from `.env` / Basic auth |
| Diagnostics on the public port | `/actuator/**`, Swagger, H2 console, `show-sql`, DEBUG logs of bound values | health + info only; metrics on a separate internal management port; the rest off |
| Gateway side doors | `/<service-id>/**` auto-routes bypassing filters; `X-User-Id` mutation silently dropped | locator disabled; one authentication filter chain for every path; CORS origins explicit |
| Containers | root, Compose ports on all interfaces | uid 10001; every published port bound to `127.0.0.1`; Kubernetes pods `runAsNonRoot`, read-only root filesystem, no capabilities, seccomp `RuntimeDefault` |
| TLS material | private key + session-ticket key committed | generated by the CA at start-up, never committed, 24 h lifetime |

## 3. Finding-by-finding status

Findings use the IDs from the review.

| ID | Finding | Status | Notes |
| --- | --- | --- | --- |
| S1 | TLS private key and ticket key committed | **Partly closed** | Removed from the tree and ignored (`*.pem`, `*.key`, `infrastructure/nginx/certs/*`). They remain in git history until you purge it. |
| S2 | JWT secret has a public default | **Closed** | The shared secret no longer exists. Issuer/JWKS/audience are required properties. Compose uses `${VAR:?...}`; Postgres/Redis/Grafana/Eureka/config passwords have no defaults. |
| S3 | Privileged accounts seeded by migrations | **Closed** | `V*__Drop_Users_Table.sql` in every service and vendor removes the table and the seeded rows, including on databases that already applied the old versions. Development users exist only in Keycloak, created by `infrastructure/keycloak/seed-dev.sh`. *Residual:* the already-applied seed migrations (`V5`/`V6`) still mention the old test password in SQL comments - Flyway checksums forbid editing them; it is removed from the database by the drop migration but stays in the repository and its history. |
| S4 | Authorization holes | **Closed** | `PUT /api/inventory`, refunds, `POST /api/payments`, the product API, notifications, customer list and order list are all restricted; ownership enforced in `CurrentUser`. |
| S5 | Duplicated, symmetric identity | **Closed** | External IdP, RS256, JWKS, audience check; per-service `users` tables dropped; no service can mint a token. *Residual:* the development client allows the password grant; no MFA configured. |
| S6 | Gateway bypass / rate limiter | **Partly closed** | Locator disabled, authentication at the edge for every path, explicit CORS, the discarded header mutation is gone with the old filter. *Open:* the rate limiter still keys on `X-Forwarded-For`, shares one counter across routes and uses a blocking Redis call. |
| S7 | Control plane open | **Partly closed** | Eureka now needs HTTP Basic; the config server has an explicit password. *Caveat:* Eureka clients carry the credentials in their `defaultZone` URL, which Netflix's client prints in some connection-error log lines. Prefer a header-based client (custom `EurekaClientHttpRequestFactorySupplier`) or move discovery to Kubernetes Services. |
| S8 | Diagnostics exposed | **Closed (public port)** | Management on a separate internal port (not published, not routed), `show-details: never`, Swagger/OpenAPI denied unless `ecommerce.security.docs-public=true`, H2 console off, `show-sql` off, DEBUG/`BasicBinder` logging removed. |
| S9 | Credentials in config | **Closed** for Postgres, Redis, Grafana, Eureka, config server | *Open:* Kafka and ZooKeeper are still plaintext and unauthenticated; Keycloak's admin and client secrets still reach it via environment. |
| S10 | Deserialization trusts `*` | **Open** | `KafkaEventConfig` and the Redis cache serializer are unchanged. |
| S11 | Validation, brute force | **Partly closed** | Stock quantities validated (controller and service); brute-force protection now comes from Keycloak (lockout after 5 failures). *Open:* `sortBy` is still passed to `Sort.by` unchecked. |
| S12 | PII in logs, GDPR/PCI docs | **Open** | Unchanged. |
| A7 | Inventory bugs | **Partly closed** | The negative-reservation bug is fixed. The "last unit can never be reserved" bug (`@Positive` rejects 0) is **not** fixed. |
| C3 / C4 | Root containers; unhardened pods | **Partly closed** | Non-root images; Kubernetes `securityContext`, read-only root filesystem, seccomp; Redis password. *Open:* NetworkPolicies are still opt-in (`k8s/hardening`), no PodDisruptionBudgets or digest-pinned images. |
| O4 | No graceful shutdown | **Closed** | `server.shutdown: graceful` with a 30 s phase timeout in every service. |

## 5. Breaking changes and how to migrate

* **Start-up needs secrets.** Run `scripts/gen-env.sh` once. Docker Compose with a Postgres profile now needs
  `--env-file .env --env-file .env.postgres` (an `--env-file` replaces the default `.env`, so list both).
* **`POST /api/auth/login` and `GET /api/auth/me` are gone.** Get tokens from Keycloak
  ([KEYCLOAK_IDENTITY.md](KEYCLOAK_IDENTITY.md#4-getting-a-token)). Postman, the Karate suite and the docs were updated.
* **Behaviour changes callers may notice:** a `USER` token can no longer list customers or all orders, create payments, refund, or change stock (403);
  another customer's record is a 404; stock quantities must be positive (400); `POST /api/orders` by a customer must be for their own `customer_id`.
* **Ports:** each service's `/actuator/prometheus` and probes moved to a management port (9080 gateway, 9081-9086 services, 9761/9888 Eureka/config).
  Prometheus targets, Docker health checks and Kubernetes probes were updated. Only the gateway (8080) is meant to be public.
* **Local data is not carried over.** The Postgres volume must be recreated (roles changed) and the old stopped containers were removed during testing.
  `docker compose down -v` is the clean way. Dev data was throwaway sample data.
* **Kubernetes:** `k8s/base/01-secrets.yaml` (a committed Secret) is gone. `scripts/gen-k8s-secrets.sh` builds the Secret and Keycloak ConfigMaps from your `.env`;
  `scripts/deploy-kind.sh` calls it. The Helm chart is not updated (see `helm/ecommerce/NOTE.md`).
* **Retired scripts:** the JWT sections of `infrastructure/scripts/rotate-secrets.sh` and `validate-secrets.sh` no longer apply.

## 6. Purge the committed key from git history

The TLS private key, CSR, DH parameters and Nginx session-ticket key were committed in `93b5eba` and are still in history. They belonged to a
self-signed `localhost` certificate, so the real-world impact is small, but keys in history are found by scanners and set a bad example. Treat them as
compromised, and note that the committed `session-logs/` transcript also contains the old seeded credentials. **This was not done for you - rewriting
history and force-pushing is your decision.**

```bash
pip install git-filter-repo
git clone --mirror <your-repo-url> repo-mirror.git && cd repo-mirror.git        # work on a fresh mirror, keep a backup
git filter-repo --invert-paths \
    --path infrastructure/nginx/certs/privkey.pem --path infrastructure/nginx/certs/session_ticket.key \
    --path infrastructure/nginx/certs/csr.pem --path infrastructure/nginx/certs/dhparam.pem \
    --path infrastructure/nginx/certs/cert.pem --path infrastructure/nginx/certs/chain.pem \
    --path infrastructure/nginx/certs/fullchain.pem --path session-logs/
git push --force --all && git push --force --tags
```

Then: every collaborator re-clones (old clones still contain the key); ask GitHub support to drop cached views of the old commits and run secret
scanning on the rewritten history; rotate anything the key or those credentials ever protected.

## 7. Known gaps and recommended next steps

Highest value first:

1. **Purge history** ([section 6](#6-purge-the-committed-key-from-git-history)).
2. **Fix the saga's inventory bug and add an outbox** (review items A1, A7) - security work does not make a lost event or an unsellable last unit go away.
3. **Make CI honest** (review C1/C2/T2): the pipeline is still red on `main`, scans are non-blocking, and the integration step needs Redis. Add secret scanning that fails the build.
4. **Gateway rate limiter** (S6): key by principal and route, use the reactive Redis limiter, trust forwarded headers only from known proxies.
5. **Kafka and the data tier in transit** (S9/S10): SASL/TLS for Kafka, TLS for Redis and Postgres, restrict trusted deserialization packages. The step-ca overlay gives you the certificates.
6. **mTLS between services or a service mesh** ([SMALLSTEP_PKI.md](SMALLSTEP_PKI.md#11-mutual-tls-between-services)).
7. **Vault on Kubernetes** with Kubernetes auth, and Vault Agent or a restart policy for the 7-day maximum database lease.
8. **Keycloak for production:** Postgres, TLS, MFA, realm managed by pipeline, no password grant, no bootstrap admin.
9. Eureka credentials out of URLs (S7 caveat), and decide whether to keep Eureka and Spring Cloud Config at all on Kubernetes.
